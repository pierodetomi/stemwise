### Steps

Each step: tests first, implementation, `make check` green, commit `M0: <what> (<ID>)`.

1. **Dependencies and CLI skeleton.** `uv add typer pydantic pyyaml numpy soundfile scipy`; entry point
   `stemwise = "stemwise.cli:app"`; the six commands of PRD §8 registered (`analyze`, `mix`, `revise`, `master`,
   `report`, `ab`); those not yet implemented exit with code ≠ 0 and "not implemented yet (Mx)".
   Error handling: domain exception `StemwiseError` ⇒ message on stderr without traceback, code 1.
   Tests: `--help` lists the commands, a stub command ⇒ code ≠ 0.
2. **Test helpers.** `tests/helpers/signals.py` (sine, silence, noise with fixed seed) and
   `tests/helpers/project.py` (writes synthetic stems and `project.yaml` in `tmp_path`). No requirement; goes into
   the commit of step 3.
3. **`project.py` (ING-1).** Pydantic models of `project.yaml` (validation per Q-11), loader with errors that cite
   field and path, paths relative to the project folder. `scripts/export_schemas.py` and target `make schemas` ⇒
   `schemas/project.schema.json`; anti-drift test.
4. **`audio_io.py` (ING-2, ING-3, ING-4, ING-6).** Reading stems as float32 `(n, channels)`, format check, sample
   rate check, padding with warning (`logging`), 24-bit WAV writing.
5. **References (ING-5).** `load_reference()` with `resample_poly` resampling (D-012).
6. **True peak (REN-5).** `true_peak_db()` in `src/stemwise/analysis/stem.py` (the file that in M1 will host
   ANA-1). Creates `docs/analysis.md` with the first entry: formula, oversampling, filter, edge handling.
7. **Bus and raw sum (REN-5, REN-7).** `src/stemwise/render/mixbus.py`: summing on a stereo bus (mono at constant
   power, D-008), trim (D-007), baseline. Sum and trim formulas documented in `docs/analysis.md`.
8. **Runs and `mix --baseline-only` (acceptance M0).** `src/stemwise/runs.py`: folder
   `runs/YYYY-MM-DDTHH-MM-SS` in local time, created with `exist_ok=False`, suffix `-2`, `-3`… if it already exists;
   created only after the project and stems are valid; injectable time for tests. CLI wiring and acceptance tests.

### Decided

- D-007 (trim), D-008 (mono on the bus), D-009 (true peak filter), D-010 (validation, `sample_rate: auto`),
  D-011 (formats), D-012 (reference resampling): answers to Q-8 → Q-13.
- D-007, clarification: attenuation also applies when the true peak is in the band (C − 0.01; C], to guarantee the
  limit on the 24-bit file.
- D-010, clarifications from the review: `mix_true_peak_db` in [−24; −3], without inf/NaN; stem ids at most 32
  characters long.
- D-013 (new): WAV files with a WAVE_FORMAT_EXTENSIBLE header (`WAVEX`) and RF64 are also accepted; W64 remains excluded.
- Minor choices from the plan, confirmed:
  - module `runs.py`;
  - warnings on stderr only until REP-1;
  - exit code 3 for commands not yet implemented, distinct from the 2 the parser uses for usage errors.

### Doubts and risks

- **PCM tolerance**: the plan foresaw 1 LSB in the round-trip tests, but 1.5 LSB is needed. libsndfile
  scales by 2^(n−1)−1 when writing and by 2^(n−1) when reading (measured deviation up to 0.9999 LSB at 16 bit),
  and at 24 bit the float32 rounding near 1.0 adds to it. It is documented in the tests.
- **True peak**: the filter is not the one of BS.1770-4 Annex 2 (D-009). A commercial meter may read a few hundredths
  of a dB more or less on peaks close to Nyquist. The 0.01 dB margin guarantees the limit with respect to *our*
  meter, not to all of them.
- **Coverage**: `make reqs M=M0` does not show REN-5 and REN-7, which the script assigns to M2. They are still marked
  in the tests (13 and 8 references).
- **Unexpected errors**: exceptions that are neither domain nor file system errors (bugs) still exit with the
  traceback. This is intentional, so as not to hide them.
- **RF64 (D-013)**: it is an extension of the letter of D-011. If you prefer to exclude it, one line is enough.

### Manual validation (for the author)

No network is needed and there are no costs. Prerequisites:

- `make setup` run;
- a real song in `local/<song>/`, with the stems exported from the DAW in `stems/` (WAV or FLAC, same sample rate)
  and a `project.yaml` like this (roles allowed in PRD §6.1):

```yaml
name: "Titolo del brano"
sample_rate: auto
brief:
  genre: "indie rock"
  mood: "caldo, intimo"
  notes: ""
stems:
  - id: kick
    file: stems/kick.wav
    role: kick
  - id: lead_vox
    file: stems/lead_vocal.wav
    role: lead_vocal
```

1. Automatic check:
   ```bash
   make check
   ```
   Expected result: `103 passed`, no format or lint errors.

2. Raw sum of the real song:
   ```bash
   uv run stemwise mix local/<brano> --baseline-only
   ```
   What to check: the command exits without errors. It prints the run folder and the line
   `baseline: … (true peak X dBTP, raw sum Y dBTP, trim Z dB | no trim)`. If there are stems of different duration,
   a `warning:` appears listing them.
   Expected result: X ≤ −3.00. The trim is present only if Y > −3.01.

3. Format, duration and true peak of the written file:
   ```bash
   uv run python -c "import sys,soundfile as sf; from stemwise.audio_io import read_audio; from stemwise.analysis.stem import true_peak_db; p=sorted(__import__('pathlib').Path(sys.argv[1]).glob('runs/*/baseline.wav'))[-1]; i=sf.info(p); print(p, i.format, i.subtype, i.channels, i.samplerate, round(i.duration,3), 's', round(true_peak_db(read_audio(p)[0]),2), 'dBTP')" local/<brano>
   ```
   Expected result: `WAV PCM_24 2 <stem sample rate>`, duration equal to that of the longest stem,
   true peak ≤ −3.0 dBTP.

4. Listening to `baseline.wav`, on headphones and on speakers. It must be the "faders at zero" sum of the stems:
   - no distortion or clipping;
   - all stems present;
   - mono stems centered;
   - stereo stems with their original image;
   - no cut at the tail.

   The volume may be lower than a finished mix: it is the effect of the trim and of the −3 dBTP margin.

5. No overwriting. Rerun the command of step 2:
   ```bash
   uv run stemwise mix local/<brano> --baseline-only
   ls local/<brano>/runs
   ```
   Expected result: a second run folder, the first one intact, and `stems/` never modified (modification dates
   unchanged). The two `baseline.wav` files are identical:
   ```bash
   shasum -a 256 local/<brano>/runs/*/baseline.wav
   ```

6. Clear error. In a copy of the song, set a wrong frequency in `project.yaml` (for example `sample_rate: 44100`
   if the stems are at 48 kHz):
   ```bash
   cp -R local/<brano> local/<brano>-err
   ```
   Then edit `local/<brano>-err/project.yaml` and run:
   ```bash
   uv run stemwise mix local/<brano>-err --baseline-only; echo "exit=$?"
   ```
   Expected result: `error: project.yaml declares sample_rate 44100 Hz but the stems are at 48000 Hz (…)`,
   `exit=1`, no new folder in `local/<brano>-err/runs`.
