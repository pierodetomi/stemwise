### Dubbi e rischi

- **Tolleranza PCM**: il piano prevedeva 1 LSB nei test di andata e ritorno, ma serve 1,5 LSB. libsndfile
  scala per 2^(n−1)−1 in scrittura e per 2^(n−1) in lettura (scarto misurato fino a 0,9999 LSB a 16 bit),
  e a 24 bit si aggiunge l'arrotondamento float32 vicino a 1,0. È documentato nei test.
- **True peak**: il filtro non è quello di BS.1770-4 Annex 2 (D-009). Un misuratore commerciale può leggere
  qualche centesimo di dB in più o in meno sui picchi vicini alla Nyquist. Il margine di 0,01 dB garantisce il
  limite rispetto al *nostro* misuratore, non a tutti.
- **Copertura**: `make reqs M=M0` non mostra REN-5 e REN-7, che lo script assegna a M2. Sono comunque marcati
  nei test (13 e 8 riferimenti).
- **Errori imprevisti**: le eccezioni che non sono né di dominio né del file system (bug) escono ancora con il
  traceback. È voluto, per non nasconderle.
- **RF64 (D-013)**: è un'estensione rispetto alla lettera di D-011. Se preferisci escluderlo basta una riga.

### Validazione manuale (per l'autore)

Non serve la rete e non ci sono costi. Prerequisiti:

- `make setup` eseguito;
- un brano reale in `local/<brano>/`, con gli stem esportati dalla DAW in `stems/` (WAV o FLAC, stessa
  frequenza) e un `project.yaml` come questo (ruoli ammessi in PRD §6.1):

```yaml
name: "Titolo del brano"
sample_rate: auto
brief:
  genre: "indie rock"
  mood: "caldo, intimo"
  notes: ""
stems:
  - id: kick
    file: stems/kick.wav
    role: kick
  - id: lead_vox
    file: stems/lead_vocal.wav
    role: lead_vocal
```

1. Controllo automatico:
   ```bash
   make check
   ```
   Esito atteso: `103 passed`, nessun errore di format o di lint.

2. Somma grezza del brano reale:
   ```bash
   uv run stemwise mix local/<brano> --baseline-only
   ```
   Cosa controllare: il comando esce senza errori. Stampa la cartella del run e la riga
   `baseline: … (true peak X dBTP, raw sum Y dBTP, trim Z dB | no trim)`. Se ci sono stem di durata
   diversa, compare un `warning:` che li elenca.
   Esito atteso: X ≤ −3,00. Il trim è presente solo se Y > −3,01.

3. Formato, durata e true peak del file scritto:
   ```bash
   uv run python -c "import sys,soundfile as sf; from stemwise.audio_io import read_audio; from stemwise.analysis.stem import true_peak_db; p=sorted(__import__('pathlib').Path(sys.argv[1]).glob('runs/*/baseline.wav'))[-1]; i=sf.info(p); print(p, i.format, i.subtype, i.channels, i.samplerate, round(i.duration,3), 's', round(true_peak_db(read_audio(p)[0]),2), 'dBTP')" local/<brano>
   ```
   Esito atteso: `WAV PCM_24 2 <frequenza degli stem>`, durata uguale a quella dello stem più lungo,
   true peak ≤ −3,0 dBTP.

4. Ascolto di `baseline.wav`, in cuffia e su casse. Deve essere la somma "a fader a zero" degli stem:
   - nessuna distorsione o clipping;
   - tutti gli stem presenti;
   - stem mono al centro;
   - stem stereo con la loro immagine originale;
   - nessun taglio in coda.

   Il volume può risultare più basso di un mix finito: è l'effetto del trim e del margine di −3 dBTP.

5. Nessuna sovrascrittura. Rilancia il comando del passo 2:
   ```bash
   uv run stemwise mix local/<brano> --baseline-only
   ls local/<brano>/runs
   ```
   Esito atteso: una seconda cartella di run, la prima intatta, e `stems/` mai modificata (date di modifica
   invariate). I due `baseline.wav` sono identici:
   ```bash
   shasum -a 256 local/<brano>/runs/*/baseline.wav
   ```

6. Errore chiaro. In una copia del brano, imposta in `project.yaml` una frequenza sbagliata (per esempio
   `sample_rate: 44100` se gli stem sono a 48 kHz):
   ```bash
   cp -R local/<brano> local/<brano>-err
   ```
   Poi modifica `local/<brano>-err/project.yaml` e lancia:
   ```bash
   uv run stemwise mix local/<brano>-err --baseline-only; echo "exit=$?"
   ```
   Esito atteso: `error: project.yaml declares sample_rate 44100 Hz but the stems are at 48000 Hz (…)`,
   `exit=1`, nessuna nuova cartella in `local/<brano>-err/runs`.
