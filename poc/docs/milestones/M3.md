### Common setup (proposal, depends on the answers to Q-30 → Q-39)

- **`Decider` interface** (PRD §7): `decide(DecisionInput) -> Decision`. `DecisionInput` contains brief, stems
  (id, role, `notes`), `analysis.json`, history (last 2 iterations: plan + evaluation, empty in M3),
  author's request (optional), iteration number and previous plan. `Decision` contains the validated plan, the
  warnings and the call log. Two implementations: `MockDecider` and `LlmDecider`.
- **Modules** (PRD §8): `decision/base.py` (interface and types), `decision/config.py` (DEC-6, `.env`),
  `decision/prompt.py` (DEC-1), `decision/validate.py` (parsing of the response, DEC-4, DEC-5),
  `decision/llm.py` (OpenRouter with `httpx`, injectable transport), `decision/mock.py` (DEC-7). The schema stays in
  `decision/schema.py`, with in addition the per-project schema sent to the model (Q-33).
- **Pure functions**: prompt, validation, change limits and the mock decider do no I/O. The only I/O of the real
  decider is the transport; the files are written by `runs.py`.
- **Flow of `mix` in M3** (Q-32 a): project → analysis → `baseline.wav` → decision → render of `iter_00/`.
  No evaluation (M4). `--decider llm|mock`, `--export-stems` allowed also with the decider.
- **Secrets**: the key is read only from the environment or from `.env` and goes only into the `Authorization` header;
  never in logs, error messages, or the repr of the configuration. A test verifies it on the files of the run.

### Steps

   `decision/validate.py`: text → plan (```` ```json ```` block, truncations, listed errors), `iteration`

### Expected doubts

- **Comparison of the models (Q-2).** The Intelligence Index measures general capabilities, not this task: the real
  comparison is on the song, by ear and on the rationales. In manual validation there will be the commands to run
  the same project with the three candidates (3 runs, total estimated cost < 1 USD).

- **`strict` subset of the providers.** It is not the same everywhere (for example on `minLength`, `const`, `anyOf` with
  `null`): I will check it with the real call; if a provider rejects the schema, the fallback is `json_object`.
- **Cost** (H5, < 0.20 USD per song). Estimate: ~8,000 tokens of analysis + ~2,500 of system prompt as input,
  ~150 tokens per stem as output (≈ 2,000 for 13 stems). With 3 iterations and some new attempts, 4–5 calls
  per song, plus the reasoning: ~0.02–0.05 USD with Haiku 5.5, ~0.17–0.31 with Terra, ~0.34–0.62 with Sol (estimates, Q-2).
  The real cost is read from `usage.cost` in the logs and decides the comparison.
- **Language of the rationales.** I ask the model to write in the language of the brief; I do not verify it automatically
  (it would need a language detection library, outside the stack): you check it in manual validation.
- **Out of scope to keep out.** No automatic retries on network errors, no response cache, no language detection,
  no iteration loop (M4).

### Doubts and risks

- **Acceptance with the real model not yet run.** The `llm` test and the real call cost money and require your key:
  I have not run them. The outcome must be noted here after manual validation (steps 2–3).
- **`strict` schema and routing** (Q-40, findings 2 and 11). `supported_parameters` from `/models` is the union over the
  providers: with `require_parameters` the combination `structured_outputs` + `seed` (+ `reasoning`) might have no
  endpoint, or a provider might reject `minimum`/`maximum` in the schema. In that case a clear HTTP
  400/404 comes out, with no new attempts.
- **Collisions dominated by the drums.** On the real song (13 stems) 9 of the 10 collisions of `masking_top` are between
  drum microphones; voice–guitars does not appear. The prompt tells the model that those collisions are physical,
  but in this way the model does not see the masking that matters most. To be observed in the rationales; a filter
  by instrument family would change ANA-9 and is a choice to make separately.
- **Lower cost than foreseen.** On the real song the prompt is about 14,600 characters (~3,700 tokens, of which
  ~2,500 analysis), against the ~15,000 tokens estimated in the plan: the Q-2 estimates are pessimistic.
- **"One or two sentence" rationales** (DEC-3): the validation only checks that they are not empty; you judge the
  length and the language (that of the brief).
- **Log of `GET /models`**: it is not a call to the model and is not saved in full; only the
  `model_parameters` read are in the log.
- **Time of `mix` on the real song**: about 3.5 minutes before the call, almost all analysis (double STFT for the
  pre-gain, already noted in M2).
- **Deviations from the plan**: `test_runs.py::test_api_key_never_written` became
  `test_cli.py::test_mix_llm_never_prints_or_writes_the_key` (plus `test_llm.py::test_api_key_never_in_logs_or_warnings`
  and the check in `test_runs.py::test_llm_run_writes_complete_logs`); `test_mock.py::test_rules` is split into one
  test per rule; `test_schema.py::test_project_schema_matches_model` is a structural comparison (fields, required fields,
  numeric limits, excluded keywords) because the stack has no JSON Schema validator.
