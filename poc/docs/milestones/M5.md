- **A revision is a new run** (Q-50): `runs/<date-time>/` with `revision.json`, `source_plan.json`,
  `source_evaluation.json`, `analysis.json`, `baseline.wav`, `baseline_evaluation.json` (copied from the source run),
  `iter_00/` (`plan.json`, `mix.wav`, `evaluation.json`, `llm_request.json`, `llm_response.json`, stems exported on
  request), `best.json`, `report.md`. The source run is not touched (verified with hashes).
- **Flow**: choice of the source run (latest with `best.json` or `--run`) → consistency check of stems and references
  (Q-52) → re-measurement of the references only for the target → **one** decision with the request as priority,
  history = source plan with its evaluation, limits of DEC-5 relative to the source plan (Q-53, Q-54) → render →
  evaluation → `best.json` = `iter_00` if it respects the constraints, without distance comparison (REV-2, Q-51) →
  report with the diff (REV-3, Q-55, Q-57).
- **Modules**: `revise.py` new (choice of the source run, consistency check, pure `plan_diff`, `Revision` model);
  `loop.py` accepts initial history and previous plan (today `run_loop` resets them at iteration 0); `runs.py` remains
  the only point that writes files (`revise_run` reuses the common part of `mix_run`); `report.py` recognizes revision
  runs; `cli.py` remains thin.
- **Decider**: the `Decider` interface does not change. `DecisionInput` already carries `request` and `history`; the
  system prompt gains the "Revision" section only when there is a request. The fake applies the keyword rules of Q-56.
- **Contracts**: `schemas/revision.schema.json` new; `stop_reason` of `evaluation.json` and `best.json` gains `revision`
  (the two schemas are regenerated). `analysis` and `mix_plan` unchanged. No new measurement: `docs/analysis.md` changes
  only for a note on revision in the section "Verification loop" (target re-measured, no choice by distance).

### Anticipated doubts

- **H5 and cost of `revise`** (D-047, M4). `mix` measured at 0.11 USD with 2 iterations; a `revise` carries the same
  analysis plus a plan and an evaluation, estimated ~0.06 USD with Sol at medium effort. The 2 revisions of protocol
  §10.2 bring the track to ~0.23–0.30 USD, above the 0.20 threshold. The decision (threshold, count of revisions outside
  H5, cheaper default model for `revise`) is yours with the measured cost.
- **DEC-5 and strong requests.** "Voce molto più avanti" ("vocal much further forward") with a vocal already at +2 dB may
  ask for +8: it arrives at +4 and the report says so. If by ear it turns out too timid, alternative (b) of Q-54 is a
  one-line change.
- **H4 is judged by ear.** The automatic test checks that the diff touches the right stems in the right direction; if
  the change "is audible" only manual validation says so (and protocol §10.2 in M7).
- **Distance in revision.** A legitimate request (vocal further forward) can move the mix away from the target: the
  report shows the distance before and after only as information, without judgment.
- **Flagged out of scope — keep out.** No multi-iteration revision, no automatic rollback or "undo", no master guided by
  words (PRD §3), no interpretation of the request outside the decider (the engine does not analyze the text, except the
  fake for tests).

- **DEC-5 in revision** (D-063): a strong change reaches at most ±4 dB of gain and ±3 dB per band; the prompt now says so

  accumulate (finding 4); "voce e basso più avanti" (vocal and bass further forward) only raises the bass because `e`

  information.
- **Deviations from the plan**:
